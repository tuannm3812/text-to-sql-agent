The problem

Most people with a question about the data cannot write SQL, and a model that runs its own SQL is not safe to trust.

  • Answers have to be checkable.The app shows the SQL, the tables it picked and why, and the schema text sent, recorded when the answer was made.
  • The database has to stay unchanged.Read-only is enforced by the application and by each engine, not by asking the model nicely.
  • Claims have to be measured.Every accuracy figure comes from a committed run with a manifest: commit, suite and database hashes, prompt hash, model and settings.
What the model sees
Schema metadataTable and column names, types, keys, CREATE TABLE DDL
Value hintsUp to six frequent values of text columns with at most 20 distinct values, labelled when cut
Value matchingBuilt, measured, off: it would send stored values matching the question
Result rowsNever. Shown to the user only

How an answer is produced

The model proposes; Python and the engine decide.

01

Read schema

The engine for the connection builds one chunk per table: DDL, keys and bounded value hints.

02

Pick tables

BM25 over names and DDL, quarter-weight BM25 over hints, name matches and character trigrams. Top 6 plus foreign-key neighbours.

03

Generate

Question plus that schema text to Ollama or Gemini, which returns one statement.

04

Read-only gate

sqlglot AST check in the engine's dialect, internals blocked, then the engine's own read-only mode, a work budget and a row cap.

05

Show the work

Rows, a chart for one-category results, the SQL, the selection report. One repair try if the run fails.

Safety

Two independent read-only guarantees on every engine, held to one conformance suite.

  • Application check.One statement, SELECT or WITH, parsed by sqlglot in the engine's dialect; writes, DDL and database internals refused.
  • Engine guarantee.SQLite read-only URI, query_only and an authorizer; DuckDB with external access off; PostgreSQL with a least-privilege role in a read-only transaction, and a refusal to connect as a superuser.
  • Verified 4 Nov 2026 against live PostgreSQL 16.45 conformance tests, 15 per engine, 0 skipped; 1,870 tests passed in the full suite.
  • Measured refusals.On the safety suite the model refused all 6 data-change requests; overall safety accuracy 73.3 % [53.3, 93.3] on 15 cases.

What the numbers say

Better retrieval did not become better answers.

  • Recall rose; accuracy did not move measurably.Dense embeddings cut the questions missing a needed table from 128 to 74, and answers on those rose from 8 to 26 correct. Elsewhere the changed table sets flipped as many answers the other way: +0.2 points overall.
  • Value hints help on Spider, not here.On this suite they do no measurable good or harm (−1.3 [−2.9, +0.2] against plain DDL): half the literals the questions need sit in text columns over the 20-value ceiling, and most shown hints repeat the evidence.
  • Speed and accuracy trade.A per-question schema stops Ollama reusing its prompt cache, so top 6 is about 2 s slower than full DDL. Sending the same schema every time was 58 % faster but cost 2.4 points. Why is not settled: those layouts change length, content and placement together. The default stays per-question selection.
  • The trade-off, observed.128 of 1,222 questions have a needed table outside the selected tables plus neighbours. They score 8 of 128 under the default against 21 to 23 with every table sent; the other 1,094 score 359 against 315 to 320. In the layouts tested the loss on the many outweighs the gain on the few; that is not a bound on what better retrieval could reach.

Limits and next steps

What these results do not show, and what comes next.

  • One model.All v2 figures use a local 9B model. Gemini is supported but unmeasured under v2: no key is configured locally.
  • One large-schema suite.Four databases from BIRD train, with the gain from two of them; other schemas are untested.
  • Not leaderboard numbers.EX is this project's typed result comparison, not each benchmark's own scorer.
  • Hint coverage.Needed literals over the 20-value ceiling are never hinted; listing more values needs a privacy decision first.
  • Missing tables.128 questions have a needed table outside what is sent; recovering them without hurting the rest is open.
  • Gemini thinking.Its thinking tokens share the 512-token output cap, so a hard question can return no SQL; measure and disable once a key is available.
