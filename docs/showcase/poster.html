Ask in English, check the SQL

Answers you can inspect, from a database it can only read.

A local or hosted model writes one SELECT; Python decides whether it runs. Every answer shows the rows, the SQL, and the exact schema text the model was given. Result rows are never sent to the model.

How an answer is produced
01

Read schema

The engine builds one chunk per table: DDL, keys, and up to six frequent values of low-cardinality text columns.

02

Pick tables

BM25, name matches and character trigrams rank tables; the top 6 plus foreign-key neighbours are sent.

03

Generate

The model returns one SQL statement for that schema and the question, nothing else.

04

Read-only gate

AST validation in the engine's dialect, then the engine's own read-only mode, a work budget and a row cap.

05

Show the work

Rows, a chart where it fits, the SQL, the tables picked and why, and one repair try on a failed run.

What the numbers say
Selection pays only at scale.On Spider and BIRD dev (at most 14 tables) choosing tables added nothing measurable; on 34- and 65-table databases it is the one measured accuracy gain.
Better retrieval is not better answers.Embeddings sent the right tables far more often, but flipped as many other answers the wrong way. Recall is reported separately from accuracy.
Speed and accuracy trade.Sending the same schema every time lets Ollama reuse its cache and is 58 % faster, but costs accuracy, so the default stays per-question selection.
