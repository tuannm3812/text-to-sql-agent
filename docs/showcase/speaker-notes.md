## Slide 3

This slide is about the problem and, just as important, what the model is allowed to see.

[Point: Schema metadata]

The model gets the structure of the database: names, types, keys and the table definitions.

[Point: Value hints]

It also gets a few common category values, so it can spell a filter correctly.

[Point: Result rows — never sent]

It never sees the rows of an answer, and a feature that would send matching stored values stays switched off, because it did not measurably help.

Reference — not read aloud

Problem and what the model sees. Source: README, What It Does. Value hints are row-derived but bounded: up to six of the most frequent values of text columns with at most 20 distinct values, labelled when the list is cut (fe90991). Question value matching is built, measured on bird_train_large (+0.4 [-0.9, +1.6]) and off by the owner's decision of 2026-10-19.

## Slide 4

Now how one question becomes an answer, left to right.

[Point: Select]

The only choice that shapes what the model sees is which tables to send: the top six plus their neighbours.

[Point: Generate]

The model writes one statement.

[Point: Check]

Then the application, not the model, decides: a parser check first, then the engine's own read-only mode.

[Point: One repair try]

If a safe query fails, the error goes back once for a repair.

Reference — not read aloud

Architecture. Source: README, Architecture and Schema RAG; docs/2_architecture.md. Scorer weights chosen 2026-10-21 on bird_train_large (text_to_sql_agent/config.py). A dense-embedding signal exists but is off by default.

## Slide 5

Safety rests on two guarantees that each hold by themselves.

[Point: Application check]

The application parses the SQL in the engine's dialect and refuses anything but a single read.

[Point: Engine guarantee]

Each engine is also opened so it cannot write, whatever the SQL says.

[Point: 45 / 0]

One conformance suite runs on all three engines, with no skips allowed, and it passed against a live PostgreSQL server on the fourth of November.

[Point: 6 / 6]

On the safety suite the model declined every request to change data. The overall safety score is 11 of 15, so this is a small suite.

Reference — not read aloud

Safety. Sources: README Safety Model; docs/0_coding_standards.md section 3 and 4; engines/duckdb.py (read_only plus enable_external_access=False). ## Slide 7

Results on the public benchmarks, with a local nine-billion-parameter model.

[Point: Spider 1.0 dev — 64.6 %]

About two in three Spider questions are answered correctly.

[Point: BIRD dev, with evidence — 35.2 %]

BIRD is much harder. Its hints are worth about ten points on the same questions.

The biggest single fix was turning the model's thinking off: with thinking on, it often ran out of tokens before writing any SQL. These are not leaderboard numbers, because the scoring is this project's own.

Reference — not read aloud

Standard benchmarks. Release runs 2026-10-10 at 7708295, qwen3.5:9b-q4_K_M, thinking off, RAG on k=6. ## Slide 8

This is the result the October work was built around.

[Point: Top 6 tables plus neighbours — 29.1 %]

On databases with 21 to 65 tables, sending the top six tables beats sending them all by 3.6 points, with 69 percent fewer prompt tokens.

[Point: Full DDL plus value hints]

The category hints that helped on Spider show no measurable effect here.

[Point: About 2 s slower]

The price is time: each question gets a different schema, so the local model cannot reuse its cache.

Reference — not read aloud

Large schemas. bird_train_large full suite, three arms at 47284f5, 2026-10-19; evidence hints on. Top 6 vs full DDL plus hints +3.6 [+1.4, +5.8], 69 % fewer prompt tokens; carried by the 65- and 34-table databases (+5 to +6 each). Full DDL plus hints vs plain DDL -1.3 [-2.9, +0.2]. Top 6 is about 2 s slower: Ollama prefills each question's schema (the 19 Oct profiling, AGENTS.md). Source: evaluation/results/bird_train_large/README.md.

## Slide 10

This slide explains why better retrieval did not mean better answers.

[Point: Dense embeddings, against the kept scorer]

Embeddings cut the questions missing a needed table from 128 to 74, and fixed many of them, but flipped about as many other answers the wrong way.

[Point: 128 with a needed table not sent]

Sending every table helps those 128 questions,

[Point: The other 1,094]

and costs the other 1,094 more. That is what these layouts did, not a limit on what better retrieval could reach. The next test is to recover the 128 without changing what the others receive.

Reference — not read aloud

Retrieval versus answers. README 'What this says'; evaluation/results/dense_embeddings and shared_layout READMEs; evaluation/results/retrieval/README.md (MRR 0.891, every needed table sent in 89.5 % at top 6).
